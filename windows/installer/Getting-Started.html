JuLenny Toolkit

Everything here runs on your machine. Your data is encrypted before it goes anywhere, and the keys never leave.

What just got installed

Desktop appA window for the whole workflow: keys, encryption, uploads, results.
Command linejulenny-toolkit, on your PATH. Everything the app does, scriptable.
MCP serverThe connector. MCP is the Model Context Protocol, the open standard for letting AI assistants use external tools, so an AI assistant such as Claude Desktop can drive the toolkit for you.
ExamplesSample data and scripts for each function, with the answer each one should produce.

You chose which of these to install, so you may not have all four.

Your working folder

You picked a working folder during setup. Everything lives there: your keys, the files you encrypt, and the results you decrypt. Two things follow from that.

Back it up, and keep it private. Your secret key shares are in that folder. Lose them and results encrypted under those keys can never be read again, by anyone, including us. There is no recovery, and that is the point.

If you use the connector, files are referred to by name alone. Copy a file into the working folder and refer to it as customers.csv, never as a full path.

Starting out

The quickest way to see the whole thing work is a self-test: your own company running a function against your own data, with no partner involved. You play both sides, and you decrypt your own result.

If you installed the connector, just ask your AI assistant for a self-test and it will walk the sequence. Otherwise the example scripts do the same thing step by step.

Check the answer, not just that it finished. Every example ships with the result it should produce. A run that completes tells you the pipeline works; a run that matches the expected number tells you it is correct. See SELF-TEST.md in the examples folder for the expected answer of each function.

Something to say to your AI assistant

Copy the files named below into your working folder, then say the line. That is the whole prompt: name the function, say which files, and let it ask you the rest. They are listed easiest first, so start at the top if you have not run one before.

Most functions come in two variants. Itemized tells you which records, positions or rules matched; count tells you only how many. The examples below use itemized because it shows what the encryption is really doing. Choose count when the point is to let a partner learn as little as possible.

Federated average. Averages two models without either side revealing its own. The simplest one to run: it needs no evaluation keys at all, and you can check the answer with a calculator.

Run a self-test of federated-average. I've put acme_model_weights.txt,
beta_model_weights.txt, scale_a.txt and scale_b.txt in the working folder.

Joint record overlap. How many records two parties share, without either revealing their list.

Run a self-test of joint-record-overlap-itemized. I've put acme-customers.csv
and beta-2match.csv in the working folder.

You get the 2 matching records written to a file, resolved from your own side. Ask for joint-record-overlap-count instead and you get just the number, 2, which is what you want when neither side should learn which records overlap.

Negotiation matrix. Finds terms both sides accept, without either revealing its limits.

Run a self-test of negotiation-matrix-itemized. I've put acceptance_matrix.txt
and offer_vector.txt in the working folder.

You get position 16, the one set of terms both sides accept. Swap in offer_vector_nomatch.txt and you get nothing back: worth running, because a function that cannot return a clean zero is not working. Use negotiation-matrix-count when you want to know only whether a deal exists, not which one.

Decision tree inference. Scores a record against someone else's model, where neither the model nor the record is revealed.

Run a self-test of decision-tree-inference. I've put tree.json and
features.json in the working folder.

Expect [0.167801, 0.832199], so class 1.

Rule-based cross-match. Checks a shared rule list against two private sets, such as drug interactions against a patient's medications. The heaviest one: it needs rotation keys, so expect several minutes of key building.

Run a self-test of rule-based-cross-match-itemized. I've put
restriction_ingredient_pairs.txt, beta_restrictions.txt and
acme_ingredients.txt in the working folder.

You should get three matches back: gluten intolerance with wheat, peanut allergy with peanuts, and celiac disease with wheat. Those are the rules in the sample where both sides have their half. Use rule-based-cross-match-count when the other side should learn only how many rules matched, not which.

Your AI assistant never sees the contents of these files, or your results. It is given file names, counts and status only. If it asks for access to your working folder, say no: it does not need it, and the answer will still come back.

How a real collaboration works

  1. Agree a collaboration with your partner on the platform, and pick the function.
  2. Build the joint key together. Each side generates a share; neither side ever holds the whole key. This takes a few rounds of exchanging files.
  3. Encrypt your data here, on your machine, and upload only ciphertext.
  4. Run the function. The platform computes on the encrypted values.
  5. Decrypt together. Both sides contribute; one of you sees the answer and shares it with the other.

Both sides must write shared records the same way. Encoding depends on the exact text, so Jane Smith,1984-12-15 and Jane Smith, 1984-12-15 will not match. Agree a format before you start.

Do not edit data files in a spreadsheet. Excel silently rewrites dates, drops leading zeros from identifiers, and changes quoting. Any of those stops your records matching the other side, and nothing will warn you: the result just comes back thin.

If something goes wrong

No matches at all The two sides encoded differently. Check the format agreement and that nothing rewrote one file.
An answer that looks wrong Usually a key problem. Check you registered the final key from each protocol, not an intermediate round.
Last decimals differ Expected. Some functions use approximate arithmetic; small deviations are normal.

Run julenny-toolkit --help, or any subcommand with --help, to see what it expects.
